# Chase_202110 — Construction of APN Permutations via Walsh Zero Spaces

**Paper**: Chase, Lisoněk. "Construction of APN permutations via Walsh zero spaces." 2021.

**Reproduction path**: `papers/2021/Chase_202110/`

**Verdict**: Mostly complete

Every numbered claim of the paper — Propositions 2.2, 3.1, Definition 3.2, Example 3.3,
Proposition 3.4, Lemma 3.5, Corollary 3.6, Propositions 4.1-4.3, Propositions 5.1-5.3,
Sections 6.1 and 6.2 — has a dedicated file mirroring the paper's numbering, and
independent recomputation confirms the implemented formulas are correct. The gaps are two
coverage claims stated in the paper's prose (the Section 5 pair-coverage claim is never
checked; the Section 4 claim is untested at n=9), plus one test that is weaker than the
report check it shadows.

> **Environment note**: Julia is not installed in the review environment, so `make test`
> could not be executed. Every numeric claim below was re-derived independently in Python
> from the `.tex` source and from the repository's own committed data, then compared against
> what the reproduction hard-codes and asserts.

## Paper Issues

### 1. Proposition 3.1 misclassifies `(0,0)` once the zero-convention is adopted

- **Location**: Section 3, statement of Proposition 3.1, read against the paragraph
  preceding Definition 3.2.
- **Computed counter-evidence**: Proposition 3.1 says "(a,b) is a Walsh zero iff
  `Tr(a·b^{−1/(2^i+1)}) = 0` **or** `a ≠ b = 0`". The paragraph before Definition 3.2 then
  declares `0^{−1/(2^i+1)} = 0` and asserts "this works correctly … for a pair `(a,0)` we
  get `Tr(a·0) = 0`, as desired". Under that convention the first clause also fires for
  `(0,0)` — but `W_f(0,0) = 2ⁿ = 32` at n=5, not 0. The two clauses are mutually
  inconsistent at `(0,0)`.
- **Severity**: cosmetic; the reproduction handles it correctly (`helpers.jl:123`
  `b == 0 && return a != 0`, and `proposition3_1.jl:32`).

### 2. Section 6.1 off-by-one in the computer-free description

- **Location**: Section 6.1: "32 of them are obtained from Proposition 4.3 with m = n = 5".
- **Computed counter-evidence**: Proposition 4.3 with `m = n = 5` yields exactly **31**
  distinct spaces (`μ` ranges over `F*₃₂`), and `Z_0b` is **not** among them — adding it to
  the set raised the cardinality from 31 to 32. The sentence should read "31 of them …
  together with the trivial `Z_0b`". The companion half is stated correctly, because there
  the paper writes "`μ ∈ F₂⁵`" (allowing `μ = 0`), giving 31 + `Z_a0` = 32.

### 3. Misattribution in the Introduction

- **Location**: Section 1.
- **Evidence**: the text credits "An infinite family of quadratic APN permutations in odd
  dimension found in 2008 by **Beierle**, Carlet, and Leander [8]"; reference [8] is
  *Budaghyan*, Carlet, Leander, IEEE-IT 54(9), 2008.

### 4. Cross-reference typos

- **Location**: the text after Corollary 3.6, and the proof of Proposition 5.3.
- **Evidence**: both cite "Lemma 3.6" for what is stated as **Corollary 3.6**. Separately,
  Section 1 attributes the `F₂⁶` APN permutation to "Dillon et al. [5] … in 2009", while [5]
  is Browning–Dillon–McQuistan–Wolfe, 2010.

### 5. Proposition 5.2's hypothesis is looser than its proof needs

- **Location**: Proposition 5.2, compared with Proposition 5.3.
- **Evidence**: Proposition 5.2 says only "ξ is a fixed element of `F₂³`", while
  Proposition 5.3 explicitly requires ξ primitive. The case analysis in the Proposition 5.2
  proof (RHS ∈ `{0,1,ξ,ξ+1}`) is degenerate for `ξ ∈ {0,1}`. The conclusion still holds —
  for `ξ = 1`, `ξ^{2^i} = ξ` makes the RHS identically 0 — but the statement should say
  `ξ ∈ F₂³ ∖ F₂` for the proof as written.

## Reproduction Issues

### 1. The Section 5 coverage claim is never checked

- **Location**: no file. The claim is the Section 5 preamble: "We checked using sboxU … that
  these constructions cover all such pairs in dimensions less than or equal to 9."
  `section4_coverage.jl` covers only the Section 4 preamble claim.
- **Symptom**: no test is named for it; `test/runtests.jl` has no `test_section5_coverage.jl`.
  Expected: an enumeration of all trivially intersecting pairs of Walsh-zero spaces at
  n = 3, 5, 7, 9, compared against the pairs generated by Propositions 5.1-5.3 plus the
  trivial pair. Actual: nothing.
- **Root cause**: only the generation side of Section 5 was implemented.
- **Resolution plan**:
  1. Add `section5_coverage.jl` calling `enumerate_wz_spaces_gold(n, i)` (already present at
     `helpers.jl:250`).
  2. Form all unordered pairs `(S,T)` with `intersects_trivially(S,T)`.
  3. Build the constructed pair set from `proposition5_{1,2,3}_pair` over all `(ξ, μ, ν)`
     plus `{Z_a0, Z_0b}`.
  4. Assert set equality at n = 3, 5 and n = 7, with n = 9 behind `full_search`.
  5. Add `test/test_section5_coverage.jl` covering n = 3 and n = 5.

### 2. Section 4 coverage at n = 9 is not covered by the test suite

- **Location**: `section4_coverage.jl:128` (`enumerate = :none` in the `__main__` block) and
  `test/test_section4_coverage.jl`, which stops at n = 7.
- **Symptom**: the test asserts `r7.n_enumerated == 256` but never asserts anything at n = 9,
  the paper's stated upper limit. `report.jl:74` does run n=9 `:stratified`, so the
  capability exists but is untested.
- **Root cause**: a runtime concern (about 30 s per the docstring) kept it out of the default
  test.
- **Resolution plan**:
  1. Add an n = 9, i = 1 stratified case to `test/test_section4_coverage.jl`, guarded by an
     environment knob (e.g. `CHASE_FULL=1`) so CI can opt in.
  2. Record the expected `n_enumerated` value once measured.
  3. Update `report.jl`'s docstring to state which `(n, i)` pairs are actually asserted.

### 3. Propositions 4.2, 5.1 and 5.2 are not exercised over their full stated ξ range

- **Location**: `proposition5_1.jl:38`, `proposition5_2.jl:55`, `proposition5_3.jl:68` — all
  use `filter(x -> x != 0 && x != 1, subfield_elements(n, 3))`.
- **Symptom**: `proposition5_1_build` reports "exhaustive over `(F_8 ∖ {0,1}) × F_{2^n}^*`",
  but Propositions 5.1 and 5.2 as stated allow **any** `ξ ∈ F₂³`, including 0 and 1.
- **Root cause**: the degenerate `ξ ∈ {0,1}` cases (where `Z` collapses to `Z_a0`) were
  excluded for interest, not for correctness.
- **Resolution plan**:
  1. For Propositions 5.1 and 5.2, iterate over all `ξ ∈ F₂³` and assert the
     trivial-intersection conclusion still holds, flagging `ξ ∈ {0,1}` as the degenerate
     branch.
  2. Keep the ξ-primitive restriction for Proposition 5.3, which the paper does state.
  3. Reword the `completeness` `print_kv` accordingly.

### 4. The `section6_2` test is weaker than the paper's claim

- **Location**: `test/test_section6_2.jl:9` (`@test issubset(r.degrees, [2, 4, 5])`) versus
  `section6_2.jl:101` (`print_check("algebraic degrees found = {2, 4, 5}", r.degrees == [2, 4, 5])`).
- **Symptom**: with `samples = 3` the test only checks that no *unexpected* degree appears.
  It would pass even if degree 4 — the paper's whole point, since it establishes
  EA-inequivalence to both `x³` and `x^{1/3}` — never occurred.
- **Root cause**: the sample size was chosen for speed, and a subset assertion was used to
  stay seed-robust.
- **Resolution plan**:
  1. Independent runs show every Proposition-5.2 pair yields degree 4 directly and every
     Proposition-5.1/5.3 pair yields degree 4 on the inverse, so `4 in r.degrees` is robust
     even at `samples = 1`.
  2. Strengthen the test to `@test r.degrees == [2, 4, 5]`, or at minimum `@test 4 in r.degrees`.
  3. Keep the seed pinned.

### 5. The number-theoretic remark after Corollary 3.6 is not reproduced

- **Location**: no file. Paper Section 3, the paragraph beginning "For i = 1 it is easy to
  see that the proof of Lemma 3.6 does not extend…" — the claim that `2^k(2^i+1)+1` is never
  a multiple of `2ⁿ−1` for `0 ≤ k < n`, `n > 3` odd.
- **Symptom**: `definition3_2.jl` verifies the *consequence* (no extra 2-dimensional
  i-compatible subspaces) but not the stated argument.
- **Root cause**: treated as prose.
- **Resolution plan**:
  1. Add a roughly 5-line predicate in `definition3_2.jl` asserting
     `all(mod(2^k * (2^i+1) + 1, 2^n - 1) != 0 for k in 0:n-1)` for odd `n` in `5:2:17` and
     all `i` coprime to `n`.
  2. Surface it as a `print_check`.

## Catalog Status

The paper claims **no new APN function** — every construction produces functions
CCZ-equivalent to a Gold function `x^{2^i+1}`. Section 6.2's degree-4 APN permutations on
`F₂⁹` are CCZ-equivalent (by Proposition 2.2, exactly) to `x³`, hence **not-new**;
`n9_Gold_x3` already covers the CCZ class.

**No catalog gaps.**

## Library-Reuse Note

Reuse is good. `gf_mul`, `gf_pow`, `gf_inv`, `gf_trace`, `gf_relative_trace`,
`primitive_polynomial`, `subfield_elements`, `parity`, `rank_f2`, `linear_basis`,
`kernel_f2`, `complete_basis`, `span_from_basis`, `extract_linear_subspaces`, `F2LinearMap`,
`F2AffineMap`, `ccz_equivalent_function`, `walsh_zeroes`, `lat`, `thickness`,
`thickness_spectrum`, `gold_apn`, `compositional_inverse`, `are_ea_equivalent`,
`are_affine_equivalent`, `are_ccz_equivalent` and the `print_*` family are all used from
core.

**No helper duplicates an exported core symbol.** Two promote-to-core candidates:

- `helpers.jl:51-61` `trace_mask` / `trace_mask_table` — the generic bridge between the
  field-trace Walsh convention (`Tr(ax + bF(x))`) and VBF's bitwise-dot LAT / `walsh_zeroes`
  convention. Nothing in `exports.jl` provides it, and any paper stated over `F₂ⁿ` needs it.
  Belongs in `packages/VBF/src/representations/finite_field.jl` as e.g.
  `trace_form_masks(n; modulus)`.
- `helpers.jl:203` and `helpers.jl:350-354` both build
  `transpose(F2LinearMap{2N,UInt32}(UInt32[b1; b2]))`, which is verbatim the **internal**
  `VBF._ccz_mapping_from_bases` at
  `packages/VBF/src/equivalence/ccz/thickness.jl:105-112`. `papers/2022/Canteaut_202205/section4_3.jl:53`
  builds the identical expression. Exporting it (e.g. `ccz_mapping_from_bases(b1, b2, N)`
  plus a `ccz_function_from_bases(F, b1, b2)` wrapper) collapses all three call sites into
  one.

`intersects_trivially` (`helpers.jl:106`) is a marginal duplicate of the
`rank_f2([b1; b2]; nbits=2N) == 2N` test used inside `is_ccz_equivalent_to_permutation`; not
worth changing.
